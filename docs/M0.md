# M0: foundations and specs

The maths, skeleton and data formats every later stage uses. Plan:
`../SORA/docs/plans/MOTION-CORE-ROADMAP_2026-10-11.md` (stage M0). Built by Opus 5.5,

## Run it

```powershell
.\setup-env.ps1                                              # once: .venv on the owner's ROCm Python
.venv\Scripts\python -m pytest versions\v2                    # the newest version's tests (M0's among them)
.venv\Scripts\python versions\v2\scripts\m0_gate.py          # measured gate values
.venv\Scripts\python versions\v2\scripts\build_skeleton.py   # rebuild the skeleton from her VRM
```

The `.venv` is created with `--system-site-packages`, so it uses the owner's existing PyTorch
2.12 with ROCm 7.14 (and numpy, onnxruntime, pytest) without downloading them again. Only
`onnx`, `onnxscript` and `ruff` are installed into it. Since 2026-10-25 M0's code lives in each
model version's own `motionlab` package (`versions/vN/motionlab`), and each version's scripts and
tests import their own copy.

## Conventions (fixed for every stage)

| Thing | Convention |
|---|---|
| Units | Metres, radians, seconds. Tick: **60 Hz** (`formats.FPS`) |
| World frame | Right-handed, **+Y up**; in the rest pose she faces **+Z** and her left is **+X** (glTF and VRM 1.0) |
| Rotation | 3×3 matrix on column vectors, batched `(..., 3, 3)`. Never Euler angles |
| 6D | The first two columns of R: `(r00, r10, r20, r01, r11, r21)`; back to R by Gram–Schmidt |
| Local rotation | Relative to the rest pose, in the parent joint's frame. **Rest frames are world-aligned**, so the rest pose is every local rotation = identity |
| Root | The hips' local rotation is her world orientation; her root position is the hips' world position |
| FK | `W_j = W_parent · R_j`; `p_j = p_parent + W_parent · offset_j` |
| ω | **Body frame**: `R(t+Δt) = R(t)·Exp(Δt·[ω]×)`, so `ω = Log(R(t)ᵀ·R(t+Δt))/Δt` (rad/s) |
| Feedback | ω in the motion state is finite-differenced from the **realised** pose, never the model's raw output |
| Integration | `rotation.integrate` re-projects onto SO(3) every tick (measured: 7e-7 orthonormality error after 100,000 float32 steps) |
| Mirroring | `M·R·M` with `M = diag(−1, 1, 1)`, plus swapping left/right joints (`skeleton.MIRROR`) |
| Angles | `atan2`, never `arccos`; square roots are clamped, so gradients stay finite at 0 and near π |

## The canonical skeleton

The **full VRM 1.0 humanoid body: 22 joints** (owner, 2026-10-11: train on the correct joints,
and deal with an avatar's missing ones at the output). Order (parents first):
- **centre:** hips, spine, chest, upperChest, neck, head;
- **arms:** left shoulder, upper arm, lower arm, hand; the same on the right;
- **legs:** left upper leg, lower leg, foot, toes; the same on the right.

- **The same body as the training data:**
  - AMASS (SMPL) and LAFAN1 both have hips → three spine joints → neck → head, with collars;
  - so every dataset maps onto this skeleton one to one, and nothing is merged in training;
  - the model is avatar-independent.
- **No fingers or eyes:** hands are one joint each, and gaze stays deterministic IK.
- **Her proportions are Alice's** (SORA's default avatar from 2026-10-11, the owner's choice;
  Seed-san before that). `versions/vN/scripts/build_skeleton.py` reads her VRM (SHA-256 recorded) from
  `../SORA/.local/avatars/Alice.vrm` into `versions/vN/motionlab/assets/canonical_skeleton.json`. It
  first checks:
  - the hierarchy (against the nearest joint the VRM has);
  - that she faces +Z and her left is +X;
  - symmetry (measured 0.03 mm) and that her feet are on the ground.

  Hips are 0.89 m up, and the head joint 1.33 m. `--vrm` builds from another VRM.
- **VRM 0.x and 1.0 both work** (`vrm.py`). Alice is VRM 0.x, which faces −Z, so her positions
  are turned 180° about the vertical to face +Z; the asset records `vrm_version` and
  `turned_to_face_plus_z`. The file is only read: her licence forbids modifying or
  redistributing it, so it stays outside git, and the asset holds only joint positions.
- **Joints her VRM lacks are placed by a measured rule:** Alice (like Seed-san) has no
  `upperChest`, so it sits 0.436 of the way from chest to neck. That figure was measured on
  `sister1.0.vrm` (N.E.K.O's avatar, which has one: 0.436, 7 mm off the line). The asset
  records this under `synthesised`.
- **Placeholders:** joint limits (degrees from rest) and ω_max until M1 measures dataset
  percentiles.

## The avatar adapter (`adapter.py`)

The model always outputs 22 joints. `AvatarMap` maps them onto any VRM avatar's joints by
composing rotations:
- **a missing leaf** (toes) is dropped;
- **a missing only child** (Alice's and Seed-san's `upperChest`) folds into its parent: `chest ← chest ·
  upperChest`;
- **a missing joint with siblings** (a neck or shoulder) folds into its single child.

Every joint the avatar has gets the exact orientation of the last canonical joint folded into
it, so everything hanging from it is unchanged. Positions above a fold shift only by that
joint's bend on a short bone. With the upper chest bent 10°, 20° or 30°, the largest shift is
1.5, 3.0 or 4.4 cm on Alice (1.8, 3.5 or 5.2 cm on Seed-san), and zero when it's straight. `avatar_skeleton(vrm)` builds
an avatar's own skeleton and map from its VRM; the VRM's required joints must be present.

## Data formats (`formats.py`)

- **Clip:**
  - local rotations as 6D `(T, 22, 6)` and root position `(T, 3)` at 60 Hz;
  - the subject, for subject-disjoint splits;
  - optional intent labels and foot/toe contacts.
- **Windows:** 120 frames (2 s), stride 30.
- **Motion state per tick** (`STATE_SIZE` = 201):
  - 22 × 6D rotations;
  - 22 × ω;
  - the root's velocity in her heading frame (sideways, up, forward), so the state doesn't depend
    on where she is or which way she faces.

## `MotionSignal` v1 (frozen)

`specs/motion_signal.v1.schema.json` and `motion_signal.py`.
- **Audio:** `rms`, `voiced`, `pitch`, `onset` from her own speech (roadmap decision 8).
- **Emotion:** valence and arousal, no labels (decision 7).

  distance to targets) is a separate M4 input.

  bump.

## The ONNX path (`export.py`)

`StepModel` is a stand-in with M1's shape:
- the motion state and signal go through encoders, then a GRU with 256 units, then 6D rotations
  out: 531k parameters;
- it runs one tick at a time as a pure function with the hidden state passed in and out.

Exported with PyTorch's dynamo exporter to a single self-contained file (2.1 MB). Unity's Sentis
has no `GRU` operator, so the export writes the GRU as its cell equations (`CellStep`: MatMul,
Gemm, Sigmoid, Tanh and element-wise ops) with the trained `nn.GRU`'s weights; `gru_operator=True`
keeps the native node. onnxruntime matches PyTorch to 1.5e-6 over 600 ticks with the hidden state
fed back, and Unity matches it to 2.5e-7 ([runtime spike](RUNTIME_SPIKE.md)).
